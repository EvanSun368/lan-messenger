# 跨城市通信：现状、安全边界与分阶段方案

状态更新：已加入可选的受管 VPN IPv4 地址策略与连接诊断，见 [VPN_USAGE.md](VPN_USAGE.md)。未部署中继、未打开公网端口、未创建用户凭据、未安装 VPN 或修改系统安全设置。真实 VPN/两地验收仍未完成。

以下“当前源码”分析保留为设计前的基线。现阶段已用显式 VPN 专用模式处理 100.64/10 精确对端、绑定接口地址、固定端口、关闭广播及跨模式不回退；它不等于后文规划的设备身份认证/加密连接层。

## 1. 结论与优先级

**近期采用用户已经管理的可信 VPN，并手动添加设备的 VPN IPv4 地址。** 它复用现有聊天、文件和投屏，不要求先搭一套账号/中继服务。只应在小范围受管设备之间试用，不能把它宣传成应用自身已具备公网身份认证或端到端加密。

**正式的“输入邀请码即可跨城”需要新的安全连接层。** 双端主动出站到可自部署中继，中继仅提供经授权的连接撮合/字节转发；应用仍须在中继连接内部完成对端身份验证和端到端加密。不能把现有 `QTcpSocket` 服务直接映射到公网，也不能仅删除 `privateAddress` 检查。

默认仍为现有 LAN 模式。用户明确启用 VPN/安全远程联系人后才使用该路径；远程连接失败不得偷偷退回未认证 LAN 连接。

## 2. 当前源码实际支持什么

检查依据：`src/node.cpp/.h`、`filetransfer.cpp/.h`、`screenservice.cpp/.h`，不是基于界面推测。

| 模块 | 实际边界 | 跨城影响 |
|---|---|---|
| Node | `start` 监听 `AnyIPv4`；UDP 广播发现；4 字节大端长度+JSON；单帧上限 1MiB，正文 128KiB | 广播通常不会穿越路由 VPN；需要手动 IP/端口；没有公网寻址/打洞 |
| 地址检查 | `requestAddress` 只接收数字地址；`remember`、入站连接均检查 privateAddress | 不支持公网 IP/域名；检查私网地址不等于认证 |
| 私网范围 | 回环、10/8、172.16/12、192.168/16、169.254/16、fc00::/7、fe80::/10 | **100.64/10 不在白名单中**，不能直接保证常见采用该段的组网 VPN 可用；IPv6 虽有检查分支，实际监听仍 AnyIPv4 |
| 身份 | 设备 ID、昵称和资料由对端声明；群首次上下文为 TOFU 声明 | 有效 UUID/私网源地址不能证明某人或设备身份；受信网内仍可冒名 |
| 聊天结果 | 持久化 ACK、逐接收人结果、同 ID 去重和待发队列 | ACK 表示应用接收落盘，不是已读；当前 ACK 未被密码学绑定至对端身份 |
| 文件 | 提议/用户确认、分块/断点、SHA256、保存路径检查、实际最终结果回执 | Hash 能检查内容一致性，不是发送人认证；提议、下载和结果仍依赖现有对端/host 规则 |
| 共享 | 访问码持有者可读取已发布目录；发布确认、撤销、路径约束；共享上下文冻结 | 访问码是 bearer capability，不能在公网明文传输；不能默认授予所有远程联系人 |
| 投屏 | 同一个 TCP 连接传 JPEG 帧；接收需确认；每帧上限 2MiB；无远程控制 | 不存在 WebRTC/TURN、拥塞自适应或互联网媒体加密；大文件可能影响同线路投屏 |

现有私网 IP/host 绑定、长度上限、目录校验、去重、回执和确认界面是有用的防护，但不能替代身份认证、传输加密或互联网抗滥用。邮件模块使用的 TLS 不会自动为聊天/文件/投屏加密。

## 3. 可先验证的 VPN 方案

### 3.1 前提

优先复用成熟方案而非自研 VPN：已有企业 VPN 或管理员维护的 WireGuard 可作为候选；Tailscale/Headscale 能简化组网，但常用 100.64/10 与当前白名单冲突，不能直接称已支持。选择哪种产品、账号、付费/自部署控制面及地址规划由用户/管理员决定，本轮不代为安装注册。不要为了兼容让 VPN 路由/地址修改影响现有网络。

1. 用户已有或自行批准配置的受管 VPN。优先端设备之间具有强密钥身份的隧道，或明确了解集中 VPN 网关的信任范围。
2. 给参与设备分配不与现有 LAN 冲突的 RFC1918 IPv4 地址，例如专门规划的 10.x 子网；不要在本轮自动改网段、开端口或安装 VPN。
3. 在应用中手动添加对端 VPN 地址及**实际监听端口**。不能假定所有实例均固定监听 45870；`Node::start` 可接受 0 并由系统分配端口。
4. VPN 管理层按设备身份限制互访；系统防火墙只允许被批准的 VPN 对端/接口访问应用 TCP 端口。应用目前监听所有 IPv4 接口，界面里填一个 VPN 地址并不能限制入站监听。
5. 关闭公网端口转发/UPnP 暴露，拒绝从互联网直接访问当前应用端口。以上安全/网络设置需用户或管理员明确批准后操作，本设计没有执行。

### 3.2 能力与不能保证的事

- 两端在线且路由可达时，手动连接有机会复用聊天/文件/投屏；需要实际两地验收，**现在尚未验证**。
- 现有发送端待发队列可以在发送端仍在线或重新启动后重试；没有远端云离线邮箱，发送端长期离线时不能代为转交。
- VPN 封装可保护其覆盖路径；若经过解密转发网关，网关的可见范围依架构而异。不能笼统宣称应用层 E2EE。
- 一个被攻陷的已批准 VPN 设备仍可能伪造 LAN ID、发送滥用请求或请求共享。VPN 身份不自动等于应用中的昵称/联系人身份。
- UDP 自动发现通常不可用，改用手动设备地址。中继 VPN/非直连链路可能增加文件传输及屏幕延迟；投屏没有码率自适应保证。
- Tailscale 一类使用 100.64/10 的配置不能直接通过当前应用地址检查。不要建议用户“一装就能用”，也不要为此全局放宽地址限制。后续若支持，需显式用户批准的接口/路由策略及自动测试。

### 3.3 验收清单

在两台受控设备、不同网络上，由用户批准 VPN 配置后：
- 指定 VPN 地址互相添加，重启后地址/端口管理行为明确；未批准来源不可访问。
- 128KiB 中文文本、群逐人 ACK、断线重连与重复消息去重。
- 小文件/大文件、暂停续传、接收拒绝、真实最终回执、hash 不符拒绝。
- 共享读取、撤销立即阻断、路径越界拒绝、切换聊天后不误下载到其他设备。
- 投屏明确接收/停止、断线后的停止提示、慢链路下 UI 不冻结。
- 不可达时明确待发/未知结果，绝不以“中继/隧道收到”冒充对方完成。

## 4. 正式安全远程连接的威胁模型

必须假设：公网被监听与篡改；中继可能被攻陷或恶意；攻击者会扫描、撞邀请码、重放、伪造设备/群、无限上传、占用连接/磁盘、发送畸形 JSON/MIME/JPEG/文件名；授权用户也可能滥用。设备本身被控制或本机恶意程序读取解密后的内容不在网络加密可解决范围内。

保护目标：
- 只有经过配对确认的设备可建立应用会话；公网上不能凭昵称、UUID、源 IP 或短邀请码取得文件/投屏权限。
- 消息/文件/投屏内容在远程路径上加密且完整性受保护；被攻陷的纯转发中继不能解密或替换内容。
- 消息与结果回执绑定同一个经验证的设备密钥身份，重放不能产生新发送/重复写入。
- 网络层授权不隐式等于文件接收、共享发布、远程截图/投屏同意；现有用户确认仍保留。
- 明确剩余元数据：中继可能知道客户端 IP、上线时间、路由标识、流量大小和通信关联；默认不记录消息正文、访问码、认证凭据或配对秘密。

## 5. 身份、配对与密钥生命周期

### 5.1 独立安全设备身份

- 在用户明确启用安全远程功能后生成每设备密钥；使用平台 CSPRNG 和成熟 TLS/加密库，不自行实现随机数/签名/握手。
- 远程联系人身份由长期公钥指纹绑定，不再以现有自声明 UUID 为信任根。现有 UUID 仅作历史/协议兼容映射，必须保存 `verified key → local contact ID` 的明确关系。
- 首阶段无“中心账号即所有设备可信”假设：每台新设备单独配对、撤销，不能以云账号登录替代对端设备验证。
- 私钥存系统凭据库/受保护密钥存储；若不可用，明确降级为用户批准的受保护本地密钥方案，不能把私钥放 README、日志或普通配置。密钥备份/导出需独立明确授权。

### 5.2 配对

- 高熵、短期、单次的邀请码用于发现/引导，不把 6 位数字直接当永久密钥。二维码/完整邀请链接应携带协议版本、随机能力值和邀请方公钥指纹。
- 双方显示可比对的密钥指纹或握手生成的短认证字符串，通过已有可信渠道核对后确认。仅 TOFU 自动接收不足以抵御首次中间人；如提供 TOFU 便捷模式必须显著标为未验证且不得自动开放共享。
- 邀请需过期、单次消费、限制尝试次数、明确接收方确认。失效/重放/转发后的处理必须可测；转发邀请不会自动绕过设备确认。
- 已配对密钥变化一律阻断并告警，不静默覆盖。恢复/换机重新核对；密钥轮换需旧身份认证且 UI 明示，新身份完全丢失时不能冒充无缝继承。
- 撤销将终止现有会话和未完成访问票据，阻止新会话；已交付到对方磁盘的文件无法远程收回，必须明确说明。

## 6. 中继 TLS 与端到端加密必须分开

建议结构：

```text
设备 A --验证服务端证书的 TLS--> 中继 <--验证服务端证书的 TLS-- 设备 B
          └── 路由连接内部：A ↔ B 已配对设备身份的 E2E 安全通道 ──┘
```

- 外层 HTTPS/WebSocket/TLS 保护客户端到中继及认证令牌。两端主动出站，用户家庭路由器无需开放入站应用端口。中继正常 TLS 证书验证失败时禁止连接，不能 ignoreSslErrors。
- 仅有两段外层 TLS 时，中继可见明文，**不是 E2EE**。
- 内层优先评估成熟 TLS 1.3 双向认证与设备证书指纹绑定，或经过审查的标准 Noise 实现；选择一个经过验证且支持目标平台的实现，不拼装“X25519+AES+自定义签名协议”。
- 对 TLS 路线：使用独立内层 TLS 引擎/成熟库支持的流式 BIO 适配，将转发流作为可靠有序字节通道；绝不能把外层 QSslSocket 的认证结果误当作内层对端认证。证书链、有效期、设备身份及已配对指纹都必须验证；导入经过用户确认的信任锚，不盲目忽略自签错误。
- 对 Noise 路线：需先验证所选实现的维护状态、标准握手模式、静态设备密钥/指纹、重放与随机数处理及 Windows 构建，不在现有代码中自写密码学原语。
- 握手绑定版本、用途、双方设备身份及会话上下文。消息/文件/投屏使用独立流 ID、严格长度和流量窗口；不同用途不可复用 nonce/key 计数器。会话重连重新握手，不允许 nonce/会话序列重用。
- 暂不实现跨设备长期离线端到端邮箱。后续若做存储转发，需单独设计预密钥/密钥轮换/撤销/离线群成员变化；TLS 会话不能直接保护中继落盘的明文队列。

## 7. 中继认证、授权与抗滥用

- 无匿名开放转发、无任意目标主机/端口参数，避免成为代理/SSRF 服务。中继只连接已授权、已配对的注册设备流。
- 中继登录身份与对端 E2E 身份是两层：设备注册需受控管理员/单次邀请，凭据短期化，令牌绑定设备与权限，支持撤销；不能把所有部署共用的一条永久 token 编进程序。
- 配额至少覆盖每设备/每账号/每 IP 的登录失败、邀请尝试、并发连接、会话创建、每分钟消息/字节、未完成流、带宽、队列长度和存储。具体数值由小规模负载测试确定，不以“无限量”为默认。
- 前置长度检查、握手/空闲/上传超时、全链路背压、连接和文件大小上限；明确慢读者行为，防止内存积压。文件流不能饿死聊天控制和停止投屏。
- 邀请和登录错误不枚举用户/设备；审计保留必要事件、脱敏路由标识、配额拒绝及撤销记录，设置保留期，不记录访问码、私钥、密码或正文。
- 服务运行最小权限、独立存储目录、可升级依赖、受保护管理接口。公网部署、DNS、证书、账号创建、费用和防火墙变更另行取得授权；当前没有执行这些动作。

## 8. 对现有协议的集成方式

新增 `SecurePeerTransport` 边界，而不是在 `Node::privateAddress` 处开洞。输入必须是“已验证身份的连接”，不是任意 `host` 字符串。

- `Node::request/requestAddress`：现有 LAN 分支保留；安全联系人通过身份解析到已认证通道。消息 handler 获得不可由 JSON 覆写的 transport identity，校验 payload sender 与绑定身份一致。
- 文件直接 `QTcpSocket`/IP/host-ticket 逻辑需要同时适配。将下载票据和 `file_result` 绑定设备密钥身份及 transfer ID，不依赖中继 IP；保留 byte offset、SHA256、拒绝/暂停/验证完成和终态防回退。
- 投屏当前是裸 JPEG TCP 流，需经安全流发送，有背压、及时停止及接收同意，不因“已经配对”而自动开始屏幕捕获。
- 共享访问票据最好增加接收人范围、过期时间、单次/次数限制；目录仍由本地显式发布。所有 bearer token 仅在已认证加密通道传递，不放 URL 查询或日志。
- 群的安全成员名单不能由任意发送者声明覆盖。远程模式须有明确版本/成员变更授权；第一阶段可采用每成员独立已配对通道进行扇出，严格校验群快照，继续逐人回执，不声称群组前向保密协议。
- 不自动把旧“可信 LAN”联系人升级成已验证远程联系人。UI 明确显示 LAN 未认证、VPN 保护路径、已验证端到端等**不同状态**。

## 9. 可验证实施阶段

| 阶段 | 可交付 | 放行条件 |
|---|---|---|
| A：只评估/准备 | 本文、现有路径边界、VPN 操作说明 | 不改网络配置、不外联部署 |
| B：受管 VPN 验收 | 两地指定 VPN IPv4、手动添加、全部现有功能回归 | 用户批准 VPN/防火墙；真实双设备测试；不宣称应用 E2EE |
| C：离线安全通道原型 | 独立可执行程序、回环临时中继、临时测试设备密钥、标准内层认证加密 | 不接生产 Node，不加载用户历史/账号；密钥错配/证书错误/重放/降级/截断/损坏/超时/内存限额负向测试；仅测试凭据 |
| D：认证一对一聊天 | 显式配对、旧 ID 映射、持久 ACK、断线重连、LAN 默认不变 | 中继看不到已知明文；伪造身份/撤销/密钥变化阻断；真实两地可靠性验证 |
| E：文件/共享 | 加密流、断点/配额/最终结果、显式接收和共享范围 | hash 错误/错误身份/票据重放/撤销/磁盘失败/慢链路回归 |
| F：群/投屏 | 受控成员快照、逐人流与回执、实时背压 | 未经同意不捕获屏幕；拒绝/停止即时；大文件不拖死聊天；多成员撤销测试 |
| G：运营可用中继 | 受控注册、监控、升级、成本/配额、备份恢复 | 独立安全审查、部署授权、隐私/日志/保留策略确定 |

### 可以下一步批准的独立原型（尚未实施）

只在本机回环运行临时 relay 和两客户端；通过审核的 TLS 实现建立双向身份验证的内层安全流，再发送固定测试文字和文件。测试配置与生产凭据分离，退出即清理临时资料。默认不连接公网、不开放公共接口、不替换当前 LAN 后端。原型必须实测加密/密钥错配与配对边界，不能仅用 base64、HTTPS 包装或换 UI 冒充 E2EE。

## 10. 当前不能对用户承诺

当前没有公网中继、NAT 打洞、互联网端到端设备身份认证、跨城自动发现、长期离线云转发、可靠的互联网群密钥管理或互联网投屏性能验证。现有 Telegram 原版 UI 组件复用不会自动带来 Telegram 云协议/安全能力。本文只是分阶段设计，除源码阅读与文档外未实施上述新增能力。
