# Actual file timeline integration

Node::recordTransferEvent records only local timeline metadata. It atomically
inserts a messages row, message_transfers mapping and author. It does not send a
chat packet, add outbox work, or infer transfer success. The local message ID
uses file:<transfer-id>, distinct from remote protocol message IDs; repeated
transfer updates do not duplicate history. Existing historical text is unchanged.
History pagination joins the mapping and orders the real timestamp/message ID.

MainWindow::appendMessage renders TransferCard only from FileTransfer's current
snapshot. File states are not inferred from placeholder text or byte count.
Incoming completed means actual hash verification and file publication completed;
outgoing sent only means local sending finished, not peer verification. File
rows never display the chat-message delivery badge. TransferChanged updates an
existing card without rebuilding on every progress chunk. First arrival uses
renderHistory(true), where true means preservePosition, so reading older content
is not forcibly scrolled to the bottom.

Group send freezes conversation ID before dialogs. Per-recipient outgoing cards
remain in that local group and identify the target device. The existing file wire
protocol has no group context, so the receiving device sees the transfer in its
one-to-one conversation with the sender. This is an explicit compatibility limit,
not full group-file protocol migration.

Card actions call actual accept/pause/reject/retry APIs. Opening requires current
completed state, matching path, a real nonsymlink file of expected size, and user
confirmation. Startup FileTransfer revalidation supplies authoritative restored
state before enabling open.

New test_transfer_timeline covers mapping rollback with an injected SQL error,
deduplication/author/time, actual two-window TCP file transfer, sent vs completed
UI state, group-outgoing/one-to-one-incoming routing, retained scroll position
while reading text history, and restart reconstruction. Runtime screenshots must
be regenerated by FULL mode before being labeled as full Telegram-source UI.

The scroll test initially exposed integer-second FileTransfer timestamps sorting
new files before earlier same-second millisecond chat messages. FileTransfer now
records the real creation time with the same millisecond precision as messages;
no synthetic timestamp/order adjustment or fixture time manipulation was used.

Final incoming-offer flow no longer forces a modal receive dialog. It records a
waiting offer and sends normal conversation unread/desktop notification according
to foreground visibility. No directory is chosen and no file is accepted until
the user clicks Receive on the card (or explicitly uses the transfer-window
entry). The integration test now uses the untouched production offerReceived
connection, checks waiting/completed=0/no destination file plus unread=1, then
clicks Receive and selects the temporary directory through the real non-native
QFileDialog. Default Qt 6.8.3 test_transfer_timeline: 4/4 passed (two functional
cases plus setup/cleanup), 1193 ms. FULL verification remains the coordinator's
next step; current /tmp screenshots were not published as FULL screenshots.
